# Tooling rules: save tokens when reading and changing code

Two tools are **mandatory** for every agent working in this repo, backend and frontend alike. They exist to keep context small: find the few lines that matter, then read only those.

## code-review-graph (navigate before reading)

A Tree-sitter knowledge graph of the repo (functions, classes, imports, calls, tests). MCP server in `.mcp.json`, data in `.code-review-graph/` (git-ignored). Installed with `uv tool install code-review-graph`.

* **Before opening files** to understand, change, debug or review code, ask the graph first:
  1. `get_minimal_context_tool(task="…")` first, with `detail_level="minimal"` wherever accepted.
  2. Find symbols with `semantic_search_nodes_tool`; trace with `query_graph_tool` (`callers_of`, `callees_of`, `importers_of`, `tests_for`, `children_of` on a file).
  3. Before changing a shared function, DTO, type or hook: check its callers / blast radius (`get_impact_radius_tool`, CLI `code-review-graph impact`).
  4. Reviews: `detect_changes_tool` / skill `review-changes`.
  5. Budget: about five graph calls per task. Then read **only** the files and line ranges the graph pointed to (`Read` with `offset`/`limit`), plus their tests.
* Project skills generated by the tool: `explore-codebase`, `debug-issue`, `refactor-safely`, `review-changes`. Use them for those tasks.
* The graph narrows scope; it does not replace the source. Read the code and its tests before editing.
* **Coverage gap:** a full `build` indexes only files tracked by git. New, uncommitted files are not in the graph yet. For those, use `Glob`/`Grep`. After committing new files, run `code-review-graph build` (hooks keep it updated afterwards).
* Hooks (`.claude/settings.json`): `update --skip-flows` after every Edit/Write, `status` on session start; a git pre-commit hook runs `update` + `detect-changes --brief`. If the graph looks stale: `code-review-graph update` (or `build`).
* CLI fallback when the MCP server is not loaded: `code-review-graph search <name>`, `query <callers_of|tests_for|children_of|…> <target>`, `impact --files <paths>`, `status`.

## RTK (compact command output)

RTK (`rtk`, installed globally with its Claude Code hook) rewrites shell commands so their output is filtered and compact (`git status` → `rtk git status`). See `~/.claude/RTK.md`.

* Run shell commands normally through the **Bash** tool; the hook adds `rtk` for you. In PowerShell, prefix it yourself where it applies (`rtk git …`, `rtk read …`, `rtk ls …`, `rtk find …`). `rtk grep` needs `grep` on PATH, which PowerShell does not have: use the `Grep` tool instead.
* Test, lint, typecheck and build runs go through `rtk` too (only failures and summaries come back). When you need the raw output to debug, use `rtk proxy <cmd>`.
* Never dump whole files, full logs or lockfiles into context. Use `head`/`tail`, `Select-Object -First/-Last`, `Read` with `limit`, or `Grep` with `head_limit`.

## Order of preference for finding code

1. code-review-graph (symbols, relations, impact).
2. `Grep` / `Glob` with narrow patterns and `head_limit` (text, config, SQL, Markdown, uncommitted files).
3. `Read` with `offset`/`limit` on the lines found. Read a whole file only when you will rewrite most of it or it is short.
4. An `Explore` sub-agent for wide sweeps: it returns the conclusion, not the file dumps.
